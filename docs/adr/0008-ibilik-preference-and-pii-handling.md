# iBilik preference-data and landlord-PII handling

iBilik's `preferences` array is the most explicit tenant-screening data of any KL source scraped so far — a literal `type: "RACE", code: "malay"/"chinese"/"indian"/"other"` field, alongside `NATIONALITY`, `OCCUPATION`, `LEASE_TERM`, `STATUS`, and `GENERAL` types ([KL iBilik PRD §6](../prd-kl-ibilik.md)). It also embeds real landlord contact info (name, phone/WhatsApp) directly in listing data ([§7](../prd-kl-ibilik.md)). Four related decisions, made together:

1. **RACE, NATIONALITY, OCCUPATION, and GENERAL preference types are stored raw and formatted into `tenant_preference_raw` for read-only display — never a filter/tool-schema parameter.** Same posture as ADR-0004/Speedhome's `propertyTenantPreference`, extended explicitly to this source rather than left to be re-derived. `preferences` is destructured by `type`, never spread or iterated generically, mirroring `speedhomeExtract.ts`'s single-choke-point pattern.
2. **`STATUS` code `couple` maps to the `mixed` gender_restriction value.** `single-female`/`single-male` map to `female_only`/`male_only`; `couple` doesn't literally mean "any gender," but folding it into `mixed` (no gender restriction) is closer to correct than inventing a fourth enum value or discarding the signal. Accepted loss: a listing that specifically wants a couple (and would reject two unrelated singles of mixed gender) reads identically to a listing with no restriction at all.
3. **`LEASE_TERM` reuses the `min_rental_duration_months` column** Speedhome's ADR-0006 created, rather than a new field — one shared "minimum lease commitment" concept across sources. Parsed from the preference code: `6-month` → `6`, `12-month-and-above` → `12`, `less-than-6-month` → `null` (no fixed number to represent; the raw preference text is still available via `tenant_preference_raw` if this ever needs surfacing).
4. **Landlord contact info (`contactInformation`, `postedBy`) is never stored.** No `contact_name`/`contact_phone` columns exist, and none are added. Same pattern as every other KL source: the listing `url` is the contact path, not a duplicated phone number in our own database. This isn't a technical limitation — the data is right there in the scraped JSON — it's a deliberate choice not to retain a third party's PII without a specific product reason to.

## Consequences

Anything that later wants to build a "filter by nationality/race" feature must treat that as reopening this ADR, not as a small addition — the data is available in principle but this decision explicitly puts it off-limits. If a real product need for landlord contact info ever arises, that's also a new decision, not an assumption that the data being present in scraped JSON already implies permission to store it.
